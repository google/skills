## Environment and install

Symptom                                                                                                                                                     | Cause                                                                                                                                                                       | Fix
----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---
`python3 -m venv ...` fails: `ensurepip is not available`                                                                                                   | Debian/Ubuntu ship the venv module separately                                                                                                                               | `sudo apt install python3-venv` (or `python3.X-venv` for a specific minor version), then rerun the `venv` command.
`ModuleNotFoundError: ai_edge_litert.aot` or `cannot import ... google_tensor`                                                                              | LiteRT not installed in the active interpreter, or an old `ai-edge-litert` without the AOT API                                                                              | Activate the venv; install as in SKILL.md step 2a.
`compile_model.py` exit 5 `cannot import the LiteRT AOT API` although the venv install succeeded                                                            | The script was started with a different interpreter (system `python3`, a tool's bundled Python) than the one the packages were installed into                               | Run it with the venv's interpreter explicitly: `~/.venvs/litert-tensor/bin/python scripts/compile_model.py ...` (the venv `--print-install` creates; no activation needed).
`pip install` fails: `SDK location is not set. Aborting installation.`                                                                                      | `GOOGLE_TENSOR_SDK_BETA` was not exported; the SDK package has no built-in download URL (observed with 2.1.6)                                                               | `export GOOGLE_TENSOR_SDK_BETA=/abs/path/litert_plugin_compiler.tar.gz` (Beta e-mail), then re-run the `pip install` line printed by `compile_model.py --print-install`.
`pip install` fails: `Google Tensor SDK beta file not found`                                                                                                | Wrong tarball path                                                                                                                                                          | Fix the path (must be an existing `.tar.gz`/`.zip` file).
`compile_model.py` exit 4 / `NotImplementedError: ... only supported on Linux x86 architecture`                                                             | Compiler plugin is Linux `x86_64` only                                                                                                                                      | Re-run with `--colab --sdk-tarball /abs/path/litert_plugin_compiler.tar.gz` (uses `google-colab-cli` to compile on a remote Google Colab Linux `x86_64` VM), or compile on a Linux `x86_64` box; benchmark from any OS with `adb`.
`compile_model.py --colab` exit 5: `'colab' CLI not found`                                                                                                  | `google-colab-cli` is not installed or not on `PATH`                                                                                                                        | Run `python3 scripts/compile_model.py --print-install --colab` for the install commands (`uv tool install`, `pipx install`, or a venv), or pass `--colab-bin /abs/path/to/colab` (or env `LITERT_GOOGLE_TENSOR_COLAB_BIN`).
`compile_model.py --colab` exit 5: `failed to query Google Colab sessions` / OAuth or ADC error                                                             | `google-colab-cli` is not authenticated yet, or `--colab-auth adc` lacks the Drive + Collaboratory scopes                                                                   | Run `colab sessions` once in an interactive terminal to complete browser OAuth (cached in `~/.config/colab-cli/`), or if using `--colab-auth adc`, run `gcloud auth application-default login --scopes="https://www.googleapis.com/auth/cloud-platform,https://www.googleapis.com/auth/drive,https://www.googleapis.com/auth/colaboratory"`.
`compile_model.py --colab` exit 5: `--colab requires the Google Tensor SDK Beta tarball` (before `colab new`)                                               | Neither `--sdk-tarball` (`GOOGLE_TENSOR_SDK_BETA`) nor `--sdk-url` (`GOOGLE_TENSOR_ML_SDK_URL`) was supplied and the target session does not already have the SDK installed | Pass `--sdk-tarball /abs/path/litert_plugin_compiler.tar.gz` (from the Google Tensor SDK Beta e-mail) or `--sdk-url <url>`. The script checks this before calling `colab new` so no Colab VM is allocated without it.
`compile_model.py` exit 5: `liblitert_plugin_compiler.so not found` / `Warning: SDK files directory not found at .../ai_edge_litert_sdk_google_tensor/data` | The SDK package was built without the Beta tarball (`SKIP_SDK_DOWNLOAD` set, or pip reused a cached wheel from an earlier attempt)                                          | Reinstall with the variable set: the `pip install` line from `compile_model.py --print-install` plus `--force-reinstall`.
Compile fails, log shows `Failed to load Tensor TPU compiler library: liblitert_plugin_compiler.so: cannot open shared object file`                         | Same root cause as above, caught at run time                                                                                                                                | Same fix; `compile_model.py` maps this to exit 5 and prints the log lines.
`compile_model.py` prints `WARNING: ai-edge-litert X and ai-edge-litert-sdk-google-tensor Y differ` (or the same for the `-nightly` pair)                   | The runtime and SDK packages were installed at different versions, e.g. one was upgraded on its own                                                                         | Reinstall both at one version with `GOOGLE_TENSOR_SDK_BETA` set: the reinstall line in the warning (pinned version, `--force-reinstall`). Compile results from a mixed pair are not a supported combination.
`compile_model.py` prints `NOTE: installed ...; versions.json pins V`                                                                                       | The venv holds a matching pair at a version other than the skill's pin (or only the nightly pair)                                                                           | Allowed: the compile uses what is installed and the sidecar records it. For the pinned pair run the reinstall line from the note. If another version should become the pin, follow `contributing.md`.
No Google Tensor backend / "unsupported target" although the SDK is installed                                                                               | `GOOGLE_TENSOR_BACKEND_ENABLED` missing with the stable package                                                                                                             | The script sets it; if you call the API yourself, `export GOOGLE_TENSOR_BACKEND_ENABLED=1` before importing `ai_edge_litert`.
`libc++.so.1: cannot open shared object file` while importing/compiling                                                                                     | Host lacks libc++ (the public Colab installs `libc++-18-dev libc++abi-18-dev`)                                                                                              | `sudo apt-get install libc++-18-dev libc++abi-18-dev` (or your distro's libc++), then retry.
pip cannot find a matching `ai-edge-litert==<pinned>` wheel                                                                                                 | Interpreter version without a published manylinux wheel (supported range: `python` in `versions.json`; for 2.1.6, `cp313-manylinux_2_27_x86_64` verified)                   | Create the venv with a Python in that range and retry; `--print-install` prints the range and warns when the current Python is outside it.

## Compilation

Symptom                                                                                           | Cause                                                                                                                                   | Fix
------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---
`INTERNAL error at compiler_plugin.cc` / SIGABRT during compile                                   | Memory sharding/truncation constraints (documented in the FAQ, mostly for non-G5 targets and large models)                              | Retry with `--truncation-type half --sharding-intensity maximum`.
"The compiler does not support layers with dynamic shapes"                                        | Dynamic tensor shapes                                                                                                                   | Re-export the model with static shapes, then recompile.
"does not support the specified device"                                                           | Wrong/unsupported target string                                                                                                         | Use exactly `Tensor_G5` or `Tensor_G6` (case-sensitive).
Compile succeeds but the report shows ops left on CPU                                             | Unsupported ops or dtypes                                                                                                               | Check the partition report; try `--int64-to-int32`; otherwise benchmark with `--allow-cpu-fallback` and note the caveat.
`compile_model.py` exit 3 `is already compiled for Tensor_G5` (or `Tensor_G6`)                    | The input is itself a compiled model (the `.tflite` carries a Google Tensor stamp)                                                      | Compile the ORIGINAL (uncompiled) export instead. `--force` is not a fix: it only skips this check, and the compiler then fails with `compiled_result or num_byte_code is nullptr` (exit 6) because it cannot recompile `DISPATCH_OP` partitions.
`compile_model.py` exit 3 `was compiled by another toolchain`, `check_compiled.py` exit 4          | The input holds an Edge TPU custom op (`edgetpu-custom-op`, `edgetpu-custom-op-2`) from the Edge TPU compiler or older Google Tensor tooling: one opaque op instead of TFLite ops (observed 2026-10-14 with files named `*_compiled.tflite`, which `check_compiled.py` reported as plain before it learned this marker) | Compile the ORIGINAL model it was made from. Such files run neither on LiteRT's Google Tensor runtime nor on the CPU, so `benchmark_on_device.py` and `package_ai_pack.py` refuse them too. Without the check, the compiler logs `selected 0 ops, from a total of 1 ops` and `compiled_result or num_byte_code is nullptr`.
`compile_model.py` exit 2 `output already exists: ... stopping so it is not overwritten`          | A file with the default name `<model>_Google_<target>.tflite` is already in the output directory (the script never overwrites silently) | Verify it with `scripts/check_compiled.py` and reuse it, or pick another name with `--output-name NAME`, or pass `--overwrite` if the user explicitly wants it replaced.
Model > 2 GB fails                                                                                | Large-model path disabled                                                                                                               | Add `--large-model-support`.
`compile_model.py --colab` exit 6: timed out during `colab exec` or killed (OOM) on the remote VM | Large model exceeded the default 900 s timeout or the standard Colab VM memory                                                          | Add `--colab-high-mem` (allocates a high-RAM Colab VM via `colab new --high-mem`) and/or increase `--colab-timeout 1800`.
Interrupted `--colab` run (`SIGKILL`) left a Colab VM session active                              | `SIGINT`, `SIGTERM`, and `SIGHUP` run the `finally:` cleanup automatically, but `SIGKILL` cannot                                        | Check `colab sessions` and stop any leftover `litert-gt-*` session with `colab stop -s <session>`.
Vague/unknown compiler error                                                                      | Limited error reporting                                                                                                                 | Retry with different flag combinations (FAQ guidance); if reproducible, file an issue on the LiteRT GitHub with the model and flags.

## adb and device

| Symptom | Cause | Fix |
|---|---|---|
| `adb not found on PATH` | platform-tools missing | Install https://developer.android.com/tools/releases/platform-tools and add to PATH. |
| `adb devices -l` prints an empty list ("no ready adb device", exit 3) | USB: cable/port or USB debugging off. Forwarded phone (serial of the form `host:port`, e.g. `localhost:41015`): the forward or `adb connect` session dropped (host sleep, SSH tunnel restart) | USB: re-plug, enable Developer options > USB debugging, accept the RSA prompt. Forwarded: `adb connect host:port` (the serial is in the user's earlier `results.json` under `device.serial`) and read its output - it exits 0 even on failure; `Connection refused` means the forward itself is down and must be re-created on the host that owns the phone (nothing on this side fixes it; retry after it is back). Prefer `adb reconnect` over `adb kill-server`, which drops every device of every user on a shared host. |
| Device listed as `unauthorized` or `offline` | USB-debugging prompt not accepted, or a stale connection | Accept the prompt on the phone, re-plug; `adb reconnect` (or `adb reconnect offline`). |
| "more than one device connected" | Several phones/emulators | Pass `--serial <id>` from `adb devices`. |
| exit 4 `model is compiled for Tensor_G6 but the device is Tensor_G5. Recompile the ORIGINAL (uncompiled) model with --target Tensor_G5; there is no runtime fallback.` (or the reverse) | Target mismatch; the script stops here, before anything is downloaded or pushed (`--output-dir` is not created) | Options, most specific first: an existing build of the same model for the phone's SoC (verify with `check_compiled.py --expect-target`), the matching phone, or a recompile of the original export. |
| With `--allow-mismatch`: model loads, delegate attaches, then every run logs `Failed to invoke SB invocation context`, `FAILED_PRECONDITION: A request is already in-flight`, `Node number 1 (DELEGATE) failed to invoke`, ending in `Benchmarking failed.` (exit 6) | A model compiled for another Tensor SoC (seen: G6 model on a G5 phone) | Recompile for the attached SoC; there is no runtime fallback. |
| `ro.soc.model` unrecognised | Unexpected device | Verify it is a Pixel 10/11; the script still runs but cannot validate the target. |
| `adb push` fails with "No space left on device" | Full phone storage | Free space or pick a different `--device-dir`. |
| User asks to clean a custom `--device-dir` that also holds their own files | Leftovers of interrupted runs are always `<base>/run-<timestamp>-<pid>/`; everything else in the base belongs to the user | `adb shell ls -la <base>` first, then remove only the `run-*` entries (by name or `rm -rf <base>/run-*`); never the base itself. The script's own run dir is created and removed per run. |

## Host-side binaries (benchmark_model, dispatch library)

| Symptom | Cause | Fix |
|---|---|---|
| exit 5 `download failed (HTTP Error 404 ...)` for `libLiteRtDispatch_GoogleTensor.so` | The chosen bucket release directory has no Google Tensor dispatch library (which directories do: the bucket table in `benchmark-flags.md`) | Use the default URLs (release from `versions.json`), or keep your `--benchmark-url` and pass `--dispatch-lib` (GitHub release zip / own build, see `benchmark-flags.md`). |
| exit 5 `download failed (<urlopen error ...>)` for either binary | No internet, or a proxy that blocks `storage.googleapis.com` | Download both files on another machine and pass `--benchmark-bin` and `--dispatch-lib`; both are plain files, no install needed. |
| `--dispatch-lib` exit 5 "not found under" / "not inside" | The directory/zip/aar does not contain `libLiteRtDispatch_GoogleTensor.so` | Point at the extracted `.so` itself (any file name is fine as long as it is an ELF shared library - it is pushed under the canonical name), or a zip that contains it. |
| `--dispatch-lib` exit 5 "is not an ELF shared library, a directory, a .zip or an .aar" | The path is a text/HTML file (e.g. a failed browser download) or something else that is not a library | Re-download the `.so`; check with `file <path>` that it is an `ELF 64-bit ... ARM aarch64` shared object. |
| Binary behaves oddly after a bucket update, or two machines report different results with the same `latest` URL | A rolling release (`latest`, `nightly`) is cached at the build that was first downloaded and never refreshed on its own | Compare the `md5` in the provenance line (`fetched <date>, md5 <hash>`) with `md5Hash` in the bucket listing `https://storage.googleapis.com/storage/v1/b/litert/o?prefix=binaries/<release>/android_arm64/`; re-run with `--refresh-binary` (re-downloads both files). `fetch date not recorded` = cached by an older script version; `--refresh-binary` adds the record. |
| exit 5 `no default download URL (cannot read .../versions.json ...)` or `(... 'binaries_release' must be ...)`, or `--print-install` exit 2 | The skill's `versions.json` is missing, not valid JSON, or has a malformed `pip_release` / `binaries_release` | Restore it from version control (format in `contributing.md`). Until then pass `--benchmark-url` (or `--benchmark-bin` + `--dispatch-lib`); compiles still run but skip the version comparison. |

## benchmark_model on the device

Symptom                                                                                                                                                            | Cause                                                                                                                                                                                                                                                                                                                 | Fix
------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---
"Requesting full delegation and CPU acceleration are incompatible"                                                                                                 | `--use_cpu=true` combined with `--require_full_delegation=true`                                                                                                                                                                                                                                                       | Never combine them; the script passes `--use_cpu=false` in strict mode.
Run dies right after `Loading shared library: .../libLiteRtDispatch_GoogleTensor.so` (before `DispatchDelegate::Initialize`)                                       | Dispatch `.so` unusable: wrong ABI/architecture, truncated download, or a build far from the runtime's release (`latest` and `2.3.0` do interoperate - verified on a Pixel 10)                                                                                                                                        | Re-run with `--refresh-binary` using the defaults (binary and library from the same release directory, `binaries_release` in `versions.json`). If you pinned `--benchmark-url`, take the dispatch library from that same release.
exit 6 `benchmark_model exited 0 but printed no results in the format this script parses` (or `printed nothing`)                                                   | The binary's output differs from what the parser (`_PATTERNS` in `benchmark_on_device.py`) knows - usually a newer or older `benchmark_model`, e.g. a freshly downloaded `latest`/`nightly`                                                                                                                           | Re-run with the default URLs, or pin a release whose output parses with `--benchmark-url .../binaries/<release>/android_arm64/benchmark_model`. Fixing the skill (update `_PATTERNS` and the output block in `benchmark-flags.md`) is described in `contributing.md`. No profiler retry is attempted - it cannot fix a format change.
**Versions** line says `DIFFERENT releases`, `but SDK package X (DIFFERENT)`, or that the two runtime binaries come from different sources                         | The model was compiled with one LiteRT release and run with binaries from another, or the binaries were mixed                                                                                                                                                                                                         | Usually still runs (nearby releases interoperate); mention it in the report's Notes. For a clean comparison use the pinned pair (`--print-install` + the default URLs) or pin `--benchmark-url` to the compile's release if that directory ships the dispatch library. A line ending `(the pair verified in versions.json)` needs no action.
Strict NPU run fails but `--allow-cpu-fallback` works                                                                                                              | Not all ops were compiled to the TPU                                                                                                                                                                                                                                                                                  | Inspect the compile report; fix the model or accept mixed timing.
Run exits non-zero only with `--use_profiler=true`                                                                                                                 | Profiler unsupported for this build/model                                                                                                                                                                                                                                                                             | The script already retries without the profiler (the first attempt's log is kept as `npu_profiled_attempt.log`); use `--no-profiler` to skip the first attempt.
Bare `ERROR: Benchmarking failed.` right after `Found async dispatch capabilities`, nothing else                                                                   | `--signature_to_run_for` named a signature the model does not have (seen with a model that has no signature defs at all)                                                                                                                                                                                              | The script now rejects an unknown `--signature` up front (exit 2, "signature '...' not found"); omit `--signature` to run the main subgraph.
exit 6 "did not finish within --timeout Ns"                                                                                                                        | Run longer than `--timeout` (default 900 s); the script kills its adb process, which also ends `benchmark_model` on the phone                                                                                                                                                                                         | Raise `--timeout`, or reduce `--num-runs` / add `--extra-arg=--max_secs=N`. No profiler retry is attempted after a timeout.
Very high `Inference (std)` or slower than expected                                                                                                                | Thermal throttling, screen off, background load                                                                                                                                                                                                                                                                       | Check the `**Thermal before NPU run:**` header line (`throttling status N (label)` from `dumpsys thermalservice`; the sensor value next to it is a single informational reading); if the status is above 0, let the phone cool, keep the screen on, rerun; try `--performance-mode sustained_performance` for steady-state numbers.
`NPU speed-up vs CPU` is below 1x (`the CPU was faster by N.NNx`)                                                                                                  | Tiny model: the fixed per-inference NPU dispatch cost dominates (a single-op model measured ~2.9 ms NPU vs ~0.08 ms CPU on a Pixel 10), so there is nothing to gain from the TPU for it                                                                                                                               | Not a fault - report it as measured. Real workloads (e.g. a 16 MB segmentation model: ~16 ms NPU vs ~118 ms CPU) show the expected gain.
`npu.log` contains `WARNING: [dispatch_delegate_kernel.cc:...] MediaTek dispatch API returned contradictory buffer requirements for Float32 tensor ...` on a Pixel | Generic log message in the shared dispatch-delegate code path (seen only with a tiny single-op model); the run still logs `Replacing 1 out of 1 node(s) with delegate (DispatchDelegate)` and finishes with results                                                                                                   | Benign - the script counts it as `known-benign` in the **Log check** line; the full list of expected log lines is in `benchmark-flags.md`.
**Log check** line shows `N unexpected WARNING/ERROR lines` (N > 0) on a run that exited 0                                                                         | `benchmark_model` logged something outside the known-benign list (new runtime message, partial delegation with `--allow-cpu-fallback`, a failed `--cpu-baseline`, ...)                                                                                                                                                | Read the **Unexpected log lines** section under the table (verbatim lines, `(xN)` = repeats). Match them against this file and `benchmark-flags.md`; quote the ones you cannot explain in the report's Notes. The table values are still real measurements.
exit 2 `--cpu-baseline must be the ORIGINAL uncompiled .tflite` (before anything is pushed)                                                                        | A compiled model was passed as the baseline; compiled models contain NPU-only `DISPATCH_OP` nodes and cannot run on the CPU                                                                                                                                                                                           | Pass the original uncompiled `.tflite` to `--cpu-baseline` (the compiled file stays as `--model`).
exit 2 `is not AOT-compiled (no DISPATCH_OP/LiteRtStamp)`                                                                                                          | An uncompiled model was passed as `--model`; the strict NPU run needs a Google Tensor-compiled file                                                                                                                                                                                                                   | Compile it first (SKILL.md step 2b), then benchmark the compiled output; the uncompiled file is only valid for `--cpu-baseline`.
"Runs (warmup / measured)" shows more runs than `--warmup-runs` / `--num-runs`                                                                                     | `benchmark_model` treats those as minimums and also enforces `--warmup_min_secs` (0.5 s) / `--min_secs` (1 s); fast models hit the time floor first                                                                                                                                                                   | Expected; report the actual counts. For exact counts: `--extra-arg=--min_secs=0 --extra-arg=--warmup_min_secs=0`.
Interrupted run left files on the phone                                                                                                                            | Process killed with SIGKILL (Ctrl-C, SIGTERM and SIGHUP all run the cleanup; verified on device)                                                                                                                                                                                                                      | `adb shell ls -la /data/local/tmp/litert_benchmark` first, then `adb shell rm -rf /data/local/tmp/litert_benchmark/run-*` (removes only this skill's per-run directories; never remove the base directory itself, which can hold the user's own files).
`**TPU tile time:** unavailable - the dispatch library returned no telemetry hook ('Accelerator returned null hooks.') ...`                                        | The dispatch library has no telemetry hooks: builds from the LiteRT GitHub source compile them out                                                                                                                                                                                                                    | Use the default bucket binaries (they have the hooks: `2.3.0` and `latest`, checked 2026-10-09; `2.3.1`, checked 2026-10-26), or skip the pass with `--no-tile-time`. The NPU numbers are unaffected.
`**TPU tile time:** inconsistent - ... the hook counted N calls for R runs, which matches no known pattern ...`                                                    | The hook's count is not (1 + D), D or 1 times the runs: e.g. a multi-signature model whose first `Replacing ...` line belongs to another subgraph, or a hook build that counts differently                                                                                                                            | Report the header's total, not a per-inference value, and say why in the Notes. If a new release changed the counting, see `contributing.md`.
`**TPU tile time:** failed - the tile-time pass failed (exit N)` or `timed out`                                                                                    | The hooked second pass crashed or timed out; the NPU run itself succeeded                                                                                                                                                                                                                                             | Read `tile_time.log`; rerun, or use `--no-tile-time --no-power`.
`**TPU energy:** unavailable - this dispatch library's power hook predates the fix ...`                                                                            | The dispatch library carries the old power hook (checked before the pass: e.g. the Maven `litert-npu-runtime-google-tensor` 2.3.0 AAR passed as `--dispatch-lib`, checked 2026-10-26, or a cache from before the 2026-10-23 re-upload of `2.3.1`), which reads the energy counter around every call and double counts | Use the default binaries (`--refresh-binary` if the cached library is old). An app's own library (`.aab`, runtime `.aar`) has the old hook if it is from runtime 2.3.0 (the 2.3.2 AAR has the fixed one, checked 2026-10-27): moving the app to the pinned runtime release (`maven_release`) brings the fix. Latency and tile time are unaffected; the energy row shows `-`.
`**TPU energy:** unavailable - the power hook could not read the TPU energy counter: '...'`                                                                        | The phone did not let the shell process read its on-device power monitor; the quoted line is the hook's own message                                                                                                                                                                                                   | Report the quoted line in the Notes. Nothing in the skill fixes it; latency and tile time are unaffected.
`**TPU energy:** unreliable - ... 2 calls per run, the pattern of the old power hook ...`                                                                          | An old power hook that the pre-check did not recognise                                                                                                                                                                                                                                                                | As for the old-hook row above; never quote its total as an energy.
`tile_time.log` / `tile_time_report.txt` say `Average TPU tile time (us): X`, about half the table's TPU tile time                                                 | An older dispatch library (`2.3.0`, or `2.3.1` as first uploaded on 2026-10-20) counts every inference 1 + D times (2x for a normal compiled model) but adds tile time once; the header then says `2 calls per run`                                                                                                   | Quote the table value; the script divides the total by the real runs. If the run used the pinned release, the cached library predates a re-upload: compare the Dispatch library md5 with `verified.binaries` in `versions.json` and rerun with `--refresh-binary`.

## Packaging for an app (`package_ai_pack.py`, the app build)

| Symptom | Cause | Fix |
|---|---|---|
| `package_ai_pack.py` exit 5 `LiteRT's AI-pack exporter is not importable` | Started with a Python that has no `ai-edge-litert` (e.g. the system `python3`) | Run it with the compile venv's interpreter, or create a venv with `ai-edge-litert` at the pinned version (the message prints the line; the Beta SDK is not needed). |
| `package_ai_pack.py` exit 5 `LiteRT's AI-pack exporter failed (...)` | The installed `ai-edge-litert` differs from the pin and its `export_lib` API changed | Install the pinned version (`compile_model.py --print-install`). If it already is the pin, `export_lib` changed in a way the skill does not know yet: see `contributing.md`. |
| exit 3 `--fallback ... is a compiled build` / `--compiled ... is not compiled for Google Tensor` | The two inputs were swapped, or the original was compiled in place | `--fallback` is the ORIGINAL uncompiled model, `--compiled` the `*_Google_Tensor_G*.tflite` builds (`check_compiled.py` tells them apart). |
| exit 2 `two --compiled builds for Tensor_G5` | Two builds stamped for the same SoC | Pass one build per SoC (the one that was benchmarked). |
| exit 2 `differs from the build its .compile.json describes` | The file changed after compiling, or the sidecar belongs to another build | Package the build that was compiled and benchmarked, or recompile. |
| exit 2 `was compiled from a different file than --fallback` | `--fallback` is not the model the build was compiled from, so the CPU and TPU paths would run different models | Pass the original from the build's sidecar (`input`); add `--allow-source-mismatch` only if that difference is intended. |
| exit 2 `output already exists` / `refusing to replace` | The output directory exists; the script replaces only packages it wrote itself | Pick another `--output-dir`, or `--overwrite` for an earlier package (it has a `pack.json` from the script). |
| exit 7 `post-export verification failed` | The exporter wrote something the checks do not expect (new LiteRT behaviour) or a template is out of sync | Nothing was left at `--output-dir`. Note the message and see `contributing.md` (the self-test reproduces it). |
| Gradle: `Plugin with id 'com.android.ai-pack' not found` | Android Gradle plugin older than 8.8, or not declared in the root `build.gradle(.kts)` | Use AGP 8.10 or newer (device targeting needs 8.10) and declare it at the root with `apply false`. |
| Kotlin: `class 'com.google.ai.edge.litert....' was compiled with an incompatible version of Kotlin. The actual metadata version is X, but the compiler version Y can read versions up to Z` | The app's Kotlin Gradle plugin is older than the Kotlin LiteRT's Kotlin API was built with (observed: LiteRT 2.3.0 needs Kotlin 2.3) | Use Kotlin `kotlin_min` from `versions.json` or newer; the package's `INTEGRATION.md` names the version. |
| Gradle: device targeting settings rejected or ignored | `android.experimental.enableDeviceTargetingConfigApi=true` missing in `gradle.properties` | Add it (INTEGRATION.md step 7). |
| Gradle `packageDebugBundle` / `packageReleaseBundle`: `All modules with native libraries must support the same set of ABIs, but module 'base' supports '[ARM64_V8A, ARMEABI_V7A, X86_64]' and module 'google_tensor_runtime' supports '[ARM64_V8A]'` | The app builds every ABI of LiteRT's native libraries, but the Google Tensor runtime has only arm64-v8a | Limit the app to arm64-v8a: `ndk { abiFilters.add("arm64-v8a") }` in `defaultConfig` (INTEGRATION.md step 6). Ask first: devices without arm64-v8a can then no longer install the app. |
| bundletool: `Module '...' refers to device groups [...] which are not in the list [...]` | The app's `device_targeting_configuration.xml` does not define a group that the AI pack or the runtime module uses | Copy the XML from the package, or merge its `<config:device-group>` elements into the app's XML unchanged. |
| bundletool: `All modules with device group targeting must support the same set of groups` | Several AI packs were packaged for different SoC sets | Package every model for the same SoCs (e.g. G5 and G6 for all), or keep one pack per app. |
| bundletool `build-apks`: `Could not extract aapt2 ... providing the path to aapt2 using the flag --aapt2` | A bundletool jar without aapt2 (the `com.android.tools.build:bundletool` artifact from Google Maven; observed with 1.18.3) | Use `bundletool-all-<version>.jar` from https://github.com/google/bundletool/releases, or add `--aapt2=<Android SDK>/build-tools/<version>/aapt2`. |
| App log `LITERT_TENSOR_RESULT {"path":"cpu","npu_error":"not a packaged Google Tensor device ..."}` | Expected on phones without a packaged SoC, and on Android builds without NPU support (LiteRT's Google Tensor check needs API 36 and a build ID not starting with `BP2A`) | Nothing to fix; the CPU model runs. |
| App log `"path":"cpu"` with another `npu_error` on a packaged Pixel | Runtime split missing, native libraries not extracted, or mismatched LiteRT releases | `adb shell pm path <app id>` must list the `google_tensor_runtime` split (install with `--device-groups=<group>` in local testing); set `useLegacyPackaging = true`; keep `litert` and `litert-npu-runtime-google-tensor` on one release. |
| `on-demand` / `fast-follow` pack never arrives in local testing | Packs come from the APK set pushed by `bundletool install-apks --local-testing`; updates are not supported | Uninstall the app, rebuild the APKs with `--local-testing`, reinstall. |
| Quick test: `./gradlew installDebug -PtensorQuickTest=<SoC>` runs the model on the CPU (`"path":"cpu"`) | `<app module>/tensor_quick_test/<SoC>/assets/` is missing (Gradle silently ignores a missing source folder), `<SoC>` is not the phone's, the Gradle block is not in the app module's build file, or `useLegacyPackaging` is not `true` | Copy the package's `quick_test/` there; use the phone's SoC with an underscore (`adb shell getprop ro.soc.model`: `Tensor G5` -> `Tensor_G5`); check the block and the packaging setting (INTEGRATION.md, "Optional: quick test without bundletool"). The `npu_error` in the log line says which. |

### Updating an app (`--update-project`)

| Symptom | Cause | Fix |
|---|---|---|
| exit 2 `no settings.gradle.kts or settings.gradle in ...` | `--update-project` names a module or another folder, not the project root | Pass the folder with the settings file; the message names it when a parent has one. |
| exit 2 `no AI pack with Google Tensor builds in ...` | The app has no AI pack with Google Tensor device-group folders | It is a new integration: run without `--update-project` and follow `INTEGRATION.md` (SKILL.md step 5a). |
| exit 2 `several AI packs ship Google Tensor builds` / `holds several models` | The project has more than one candidate | Pass `--pack-name` / `--model-name` with one of the names the message lists. |
| exit 2 `device group ... selects several SoCs` | One group lists several `system-on-chip` selectors, but a compiled build runs on one SoC only | Give each SoC its own group, as LiteRT's exporter does, then re-run. |
| exit 2 `cannot tell where the app keeps the original (CPU) model` | The CPU copy is neither in the pack's `#group_other` folder nor at `litert/<model>_cpu_gpu.tflite` or the loader's `CPU_MODEL_ASSET` | `--cpu-asset <path in the project>` (the message lists the models it found), or `--cpu-asset none` if the app has no CPU copy. |
| exit 2 `uses <mode> delivery ... --update-project keeps it` | `--delivery` differs from the pack's `deliveryType` | Drop `--delivery`. To change the mode, edit `deliveryType` in the pack's build file first (and add the permissions a new package's `INTEGRATION.md` lists for `fast-follow` / `on-demand`). |
| exit 7 `changed in the project while the update was prepared` | A project file changed during the run | Re-run when the project is not being edited. |
| Verdict `structural`, `Model inputs/outputs` = `edit` | The new model's inputs or outputs differ in shape, type or count from the app's CPU copy | Update the app's pre- and post-processing (`model_io.json` lists the new ones) together with the files. |
| `Runtime` = `device` | The app's runtime is not `maven_release`, or its version could not be read | Run the strict benchmark with the app's library: `benchmark_on_device.py --dispatch-lib <app .aab, runtime .aar or .so>` (UPDATE.md section 4). If it fails, upgrade `litert` and the runtime together. |
| After copying, the dry run still shows `replace` | A file was not copied, or was copied to another path | Copy the rows still marked `replace` from `files/<path>`; paths are relative to the project root. |

### Applying the plan (`--check-project`) and checking on a Pixel (`install_and_verify.py`)

| Symptom | Cause | Fix |
|---|---|---|
| `--check-project` exit 2 `no readable pack.json` / `was not written by package_ai_pack.py` | `--package` is not a folder that `package_ai_pack.py` wrote | Pass the package folder (the one with `INTEGRATION.md` and `pack.json`), by default `<model dir>/app_package/<name>`. |
| `--check-project` exit 2 `no app module :<name> in ... (app modules found: ...)` | The project has no module by the package's (or `--app-module`'s) name, and not exactly one app module | Pass `--app-module` with one of the modules the message lists. |
| `--check-project` `NOTE: the package was made for the app module :app; this project's app module is ...` | The package was written for another app module name; its runtime module depends on that module | Re-package with `--app-module <the project's app module>` (SKILL.md step 5a), then check again. |
| `--check-project` exit 1 | Requirements of `INTEGRATION.md` are not met yet: this is the plan, not an error | Apply the `fail` items once the user approves (SKILL.md step 6); risky items need their own OK. |
| `--check-project` warns `no minSdk in ...`, `Android Gradle plugin: version not found` or `Kotlin: version not found` | The value is set outside the files the check reads (a convention plugin, `buildSrc`, a variable from another file) | Check it by hand: `minSdk` 31 or higher, the Android Gradle plugin 8.10 or newer, Kotlin `kotlin_min` or newer (`INTEGRATION.md` names the version). |
| `--check-project` `Kotlin: the app module applies no Kotlin plugin` | A Java-only app; `TensorModelLoader.kt` is Kotlin | Adding Kotlin is a risky item: ask first. With the Android Gradle plugin 9 or newer it is only a warning, because the plugin can compile Kotlin itself. |
| `install_and_verify.py` exit 2 `adb not found` / `java not found` / `Gradle not found` | The Android SDK platform-tools, a JDK or the Gradle wrapper is missing | Install platform-tools, set `JAVA_HOME` to a JDK the project's Gradle supports, and use a project with `./gradlew` (or pass `--gradle`). |
| `install_and_verify.py` exit 2 `need exactly one device, found ...` | No phone, a phone that has not accepted USB debugging, or several phones | Connect the Pixel and accept the prompt, or pass `--serial`. |
| `install_and_verify.py` exit 2 `cannot tell the app module` | Several modules (or none) apply `com.android.application` | Pass `--app-module`. |
| `install_and_verify.py` exit 3 `the Gradle build failed` | The project does not build: often a JDK its Gradle does not support (`Unsupported class file major version`), or a mistake in an edit | Read `gradle.log` in the output folder. Use a supported JDK; fix errors the edits caused, and report errors that were there before. |
| `install_and_verify.py` exit 3 `the build wrote no .aab to .../bundle/debug` | The app has product flavors, so its bundles are per flavor (`bundle/freeDebug/`, ...) | Pass `--variant <flavor>Debug`, for example `--variant freeDebug`. |
| `install_and_verify.py` exit 4 `cannot download .../bundletool-all-...jar` | No internet, or GitHub is blocked | Download a `bundletool-all` jar elsewhere and pass `--bundletool <jar>` (a folder with bundletool and its dependencies from Google Maven also works). |
| `install_and_verify.py` exit 4 `bundletool install-apks failed` | The phone refused the APK set, e.g. `INSTALL_FAILED_OLDER_SDK` (the app's `minSdk` is above the phone's API level) or too little storage | Read `install_apks.log` in the output folder. |
| `install_and_verify.py` exit 6 (no result line) | The app did not call `TensorModelLoader.load()` within `--timeout`, or it crashed | Open the screen that uses the model while the script waits, or raise `--timeout`. For a crash: `adb logcat -b crash -d`. |
| `install_and_verify.py` exit 7 `is already installed` | Local testing cannot update an installed app | Ask the user (uninstalling deletes the app's data on the phone), then rerun with `--uninstall-first`. |
| `install_and_verify.py` exit 1 and `Dispatch library on the phone: NO` | The runtime split is missing from `Installed:`, or native libraries are not extracted | Check the device groups and `useLegacyPackaging = true`: `--check-project` reports both. |
| `Expected path: CPU (Android API ...; the NPU needs API 36 or newer)` or `(build ... has no NPU support)` | The phone's Android build does not support the Google Tensor NPU | Not an app problem; the CPU result is correct there. Update the phone, or test on another one. |
